Jenkins 배포 호흡이 길어졌을 때, Claude Code aws-deploy 스킬로 바꾼 이유

작성일 2026-05-26 Edited on 2026-05-27 In 인프라

기존에는 Jenkins Pipeline Job으로 Lambda를 배포했다.

develop 브랜치에 PR merge가 끝나면 Hook으로 Jenkins Pipeline Job이 실행된다. Pipeline 안에서는 hook 기반으로 감지된 branch를 확인하고, git checkout .으로 반영되지 않은 변경사항을 초기화하고, 배포 대상 branch를 checkout 해서 최신화한다. 그 다음 merge 이전 HEAD 이후 변경사항을 확인하고, 변경된 Lambda 함수를 찾고, 해당 함수 배포에 필요한 기존 메타데이터와 Layer 정보를 수집한 뒤 zip으로 압축해서 배포한다.

이 방식은 틀린 방식이 아니었다. 오히려 많은 Lambda 함수를 한 저장소에서 관리하는 상황에서는 꽤 현실적인 방식이었다.

그런데 관리하는 Lambda 함수 수가 많아지면 이야기가 조금 달라진다. Lambda 하나만 수정해도 git에서 관리되는 Lambda 전체를 확인하고, 변경된 함수인지 판단하고, 기존 설정과 Layer 정보를 다시 모으는 시간이 들어간다. 빌드 자체보다도 merge 이후 deploy까지 이어지는 호흡이 길어졌다.

AI를 이용해서 개발 속도가 빨라지기 시작하니 이 차이가 더 크게 느껴졌다. 코드 수정, 리뷰, merge까지의 속도는 빨라졌는데, 그 다음 deploy까지의 감각은 예전 Jenkins 호흡 그대로였다.

그때부터 이 방식이 지금 작업 흐름과는 조금 안 맞는다는 생각이 들었다.

Jenkins가 문제였다는 뜻은 아니다

Jenkins Pipeline은 이미 많은 일을 하고 있었다.

  1. Hook 기반으로 배포 대상 branch 감지
  2. 작업 디렉토리 초기화
  3. 배포 branch checkout과 최신화
  4. merge 이전 HEAD 이후 변경사항 확인
  5. 변경된 Lambda 함수 탐지
  6. 대상 함수의 기존 메타데이터와 Layer 정보 수집
  7. zip 압축
  8. Lambda 코드 배포
  9. version publish와 alias 갱신

그러니까 이건 “zip만 올리는 스크립트”가 아니었다. 변경된 Lambda만 골라 배포하고, Lambda version과 alias까지 이미 관리하고 있었다.

문제는 자동화 품질보다 호흡이었다.

Jenkins는 안정적인 중앙 실행 주체다. 대신 내가 지금 보고 있는 로컬 변경사항, 방금 AI와 수정한 맥락, 급하게 확인하고 싶은 배포 범위와는 한 박자 떨어져 있다. merge를 하고, Hook을 기다리고, Pipeline이 자기 순서대로 작업을 끝낼 때까지 기다리는 구조다.

예전에는 그게 자연스러웠다. 그런데 AI를 붙인 뒤에는 개발 템포가 먼저 빨라졌고, deploy까지의 대기 시간이 상대적으로 더 크게 느껴졌다.

급할 때 AWS CLI로 직접 배포해봤다

그래서 급할 때는 Jenkins를 쓰지 않고 AWS CLI로 직접 배포를 몇 번 했다.

말 그대로 수동 배포였다.

  • 변경된 Lambda를 확인하고
  • 기존 설정과 Layer를 보고
  • zip으로 묶고
  • update-function-code를 실행하고
  • 새 version을 publish하고
  • alias를 맞추고
  • 필요한 경우 Step Functions까지 같이 반영했다

이 방식은 장기적으로 좋은 방식이 아니다. 사람이 계속 기억해야 하고, 순서 하나 빠지면 사고가 난다.

그런데 한 가지는 분명했다.

내가 어떤 Lambda를 왜 지금 배포하는지, 무엇이 같이 바뀌어야 하는지, 어느 지점까지 확인해야 하는지가 내 작업 맥락 안에 그대로 있었다.

Jenkins는 안정적이지만 배포를 “파이프라인이 처리하는 일”처럼 느끼게 했다. 반대로 AWS CLI 수동 배포는 위험하지만, 배포를 “내가 지금 하고 있는 작업의 연장”으로 느끼게 했다.

이 감각이 중요했다.

전환점은 “현재 작업한 사항 DEV에 배포준비해줘”였다

수동으로 몇 번 배포했던 패턴이 남아 있는 상태에서 Claude Code CLI에 이렇게 입력했다.

현재 작업한 사항 DEV에 배포준비해줘

그랬더니 Claude Code가 내가 이전에 수동으로 지시했던 사항을 단계별로 밟아가기 시작했다.

여기서 중요한 건 “Claude가 알아서 AWS 배포를 이해했다”가 아니다.

내가 반복해서 하던 작업이 이미 충분히 절차화 가능한 패턴이었다는 점이다. Lambda를 찾고, 설정을 보고, Layer를 확인하고, 배포 순서를 잡고, Step Functions 영향 범위를 확인하는 과정이 머릿속 암묵지가 아니라 언어로 풀 수 있는 절차였다는 걸 그때 봤다.

그 순간 판단이 섰다.

Pipeline에서 하는 일들 중 일정 부분은 스크립트화하고,
일정 부분은 Claude Code CLI에서 사용하는 Skills로 만들 수 있겠다.

이게 aws-deploy 스킬의 시작이었다.

그래서 만든 것이 aws-deploy 스킬이다

aws-deploy는 “Jenkins보다 빠른 배포 명령” 하나를 만든 작업이 아니었다.

내가 실제로 배포할 때 머릿속에서 밟던 판단 과정을 Claude Code 안으로 옮긴 작업에 더 가까웠다.

현재 스킬의 흐름은 대략 이렇다.

  1. 현재 branch와 배포 환경 결정
  2. 변경 파일 감지
  3. 변경된 Lambda 함수 추출
  4. 대상 함수의 기존 설정과 Layer 정보 확인
  5. 필요한 경우 Layer 반영
  6. Lambda 코드 배포
  7. Lambda version publish와 alias 처리
  8. 연관된 Step Functions definition 수정
  9. state machine version publish
  10. alias routing 재검증
  11. dry-run 성격의 사전 검증

이 중 일부는 스크립트가 하는 게 맞다. 변경 파일을 계산하거나 Lambda 디렉토리명을 함수명으로 바꾸는 일은 반복 가능한 로직이다.

반대로 일부는 Skills에 남기는 게 맞았다. 어떤 환경으로 배포할지, 어떤 프로젝트 규칙을 적용할지, Step Functions까지 같이 봐야 하는지, 사용자가 “준비”만 요청한 건지 실제 배포까지 요청한 건지 같은 판단은 작업 맥락이 중요하다.

그러니까 핵심은 이거다.

기계적으로 반복되는 부분은 스크립트로 빼고, 작업 맥락이 필요한 판단은 Skills에 남겼다.

변경 감지는 더 넓은 기준으로 본다

Jenkins도 변경된 Lambda만 배포한다. aws-deploy도 바뀐 것만 배포한다.

차이는 기준점이다.

Jenkins는 merge 이후 Pipeline 안에서 정해진 기준으로 변경 파일을 본다. 반면 aws-deploy는 내가 지금 작업 중인 로컬 상태를 기준으로 본다. upstream 기준점, push되지 않은 커밋, 워킹 트리의 dirty 변경까지 같이 본다.

이 방식이 Jenkins보다 항상 낫다는 뜻은 아니다. Jenkins는 merge 이후 중앙에서 동일한 기준으로 실행된다는 장점이 있다.

다만 Claude Code CLI에서 작업하던 흐름에서는 로컬 맥락까지 포함하는 편이 더 자연스러웠다. “내가 지금 수정한 것”을 기준으로 DEV 배포 준비를 하려면, 아직 push하지 않은 변경이나 working tree 상태도 같이 봐야 했다.

실제 실행 결과도 그랬다.

lambda_function.py 파일 1개 수정 -> {서비스명}-DEV-EDU-functionName 1개만 배포 대상으로 잡혔다.

Lambda 배포 이후가 더 중요했다

Jenkins와 aws-deploy의 차이는 변경 감지보다 그 뒤에 있었다.

Jenkins도 Lambda 코드 배포, version publish, alias 갱신까지 처리하고 있었다. 그런데 현재 Pipeline 기준으로는 Step Functions definition 교체, state machine version publish, alias 재검증까지는 한 흐름으로 묶여 있지 않았다.

서버리스 배포에서 이 지점은 꽤 중요하다.

Lambda 코드를 올렸다고 해서 Step Functions가 새 코드를 호출하는 건 아니다. Step Functions definition 안에 어떤 Lambda ARN이 박혀 있는지, 그 ARN이 어떤 version을 가리키는지, state machine alias가 새 version으로 옮겨졌는지까지 봐야 한다.

이걸 사람이 매번 기억해서 수행하면 언젠가 빠진다. 그래서 이 부분은 스킬 안에 절차로 묶었다.

aws-deploy의 차이는 “변경 Lambda를 더 잘 찾는다”보다, Lambda 배포 이후에 남아 있던 서버리스 전환 작업까지 한 흐름으로 묶었다는 데 있다.

“배포준비”와 “배포”를 나눈다

Claude Code CLI에 배포준비해줘라고 말했을 때 바로 쓰기 작업으로 들어가면 위험하다.

그래서 먼저 분석한다.

Lambda 1개 수정했는데 SF가 2개 뜬 것은, 두 SF의 definition 안에 해당 Lambda ARN이 있어서다. 수동으로 “어느 SF에 영향 가나”를 추적하지 않아도 된다.

여기서 dry-run은 사후 검증이 아니다. 쓰기 전에 영향 범위와 절차를 먼저 끊어보는 사전 검증 모드다.

이 구분이 있어야 Skills를 배포 도구로 쓸 수 있다. 자연어로 지시한다고 해서 바로 운영 리소스를 바꾸는 구조면 오래 못 쓴다. 먼저 준비하고, 보여주고, 사용자가 진행을 확정한 뒤 쓰기 작업으로 넘어가야 한다.

프로젝트 규칙은 projects/{서비스명}.md로 뺀다

스킬 자체는 기존 프로젝트 기준으로 만들었다. 다른 프로젝트에 붙이려면 projects/{서비스명}.md 파일 하나를 추가한다.

프로젝트마다 다른 부분은 AWS profile, alias 형식, 배포 제외 Lambda 목록이다. 이걸 파일로 빼면 스킬 코어를 건드리지 않고도 프로젝트별 규칙을 읽을 수 있다.

이 구조의 가치는 재사용성보다 배포 규칙의 외부화에 있다. 내 머릿속에 있던 예외와 명명 규칙이 파일로 빠져나오는 순간, 개인 루틴이 팀이 읽을 수 있는 절차가 된다.

숫자는 보수적으로 읽는다

속도 이야기를 완전히 뺄 수는 없다. 실제로 Jenkins 대기 호흡이 길어졌고, aws-deploy Stage 1 분석은 빠르게 끝났다.

확인된 값은 여기까지다.

  • Jenkins 단건 E2E: 67초
  • Jenkins 평균 빌드 시간: 139.5초
  • Jenkins 평균 대기 포함 총 평균: 약 2분 27초
  • aws-deploy Stage 1 분석: 4.57초

다만 이 숫자를 “Jenkins보다 몇 배 빠른 배포기”로 읽으면 글의 방향이 틀어진다.

4.57초는 변경 파악과 배포 대상 분석 시간이다. 실제 write 단계 전체 시간은 별도 실측으로 더 닫아야 한다. 예전에 적었던 약 25초도 확정된 E2E 실측이라기보다 체감 추정치로 보는 게 맞다.
–실제로 LLM의 상황에 따라 1건의 경우에도 Jenkins보다 더 오래 걸리는 경우도 있었다.

항목 Jenkins aws-deploy 스킬
Lambda 1개 수정 E2E 67초 (실측) Stage 1 4.57초 (실측)
전체 평균 (n=14, 대기 포함) 약 2분 27초 별도 E2E 실측 필요
변경 감지 기준 Pipeline 실행 기준 upstream + 미커밋 포함
Lambda version·alias 있음 있음
SF definition 교체 없음 (수동) 자동
SF version·alias 재검증 없음 (수동) 자동
dry-run 성격 없음 사전 영향 범위 분석
프로젝트 추가 Jenkinsfile 복사·수정 projects/{name}.md 추가

숫자는 계기였다. 진짜 주제는 속도가 아니라 작업 호흡과 배포 완료 기준을 다시 잡은 것이다.

Jenkins 대신 Skills를 선택할 때 포기하는 것

이 스킬은 Jenkins를 완전히 대체하는 범용 CI가 아니다.

Jenkins에는 빌드 이력 UI가 있고, 콘솔 로그가 남고, 중앙에서 누가 언제 무엇을 배포했는지 보기 쉽다. Slack 알림이나 감사 추적도 붙이기 좋다. 여러 사람이 독립적으로 배포하는 팀이라면 이 장점이 크다.

반대로 aws-deploy는 로컬 Claude Code CLI와 AWS 자격증명에 의존한다. 중앙 감사 추적도 약하다. Jenkins와 병행 운영하면 공식 배포 경로가 둘로 갈라질 위험도 있다.

그래서 이 방식은 모든 팀에 맞는 정답이 아니다.

소수 인원이 배포를 직접 관리하고, 로컬 작업 맥락에서 변경 분석과 배포 준비를 빠르게 이어가야 하는 경우에 맞다. 다수 팀원이 독립적으로 배포하고 중앙 UI·감사·알림 체계가 중요하다면 Jenkins가 더 맞다.

내가 이 글에서 진짜 말하고 싶은 것

이 글은 Jenkins를 깎아내리는 글이 아니다.

Jenkins는 이미 변경된 Lambda를 골라 배포하고, version과 alias까지 관리하는 파이프라인이었다. 내가 문제라고 느꼈던 건 자동화의 품질이 아니라, AI를 이용한 빠른 개발 호흡 안에서 deploy까지 이어지는 감각이 점점 맞지 않게 된 부분이었다.

aws-deploy 스킬은 그 틈을 메우기 위해 만든 것이다.

  • 반복하던 수동 배포 절차를 쪼개고
  • 스크립트화할 부분은 스크립트로 빼고
  • 작업 맥락이 중요한 판단은 Skills로 남기고
  • 결국 Lambda 이후 Step Functions 전환까지 이어지는 절차를 한 흐름으로 묶었다

내가 처음 기대했던 것도 사실 “배포가 몇 배 빨라질까”가 아니었다.

오히려 내가 실제로 일하는 방식이 얼마나 자연스럽게 자동화로 옮겨질 수 있나에 더 가까웠다.

마무리

여태까지 인프라만 알고 있던 DevOps나 인프라 담당자도, 꼭 MCP처럼 외부로 시스템을 꺼내지 않아도 된다.

자신이 반복해서 수행하는 작업 과정을 Skills로 프로세스화하면, 자기 업무를 자동화하는 동시에 나중에는 회사 동료들과도 그 흐름을 공유할 수 있다.

그게 안정화되면 단순한 개인 자동화를 넘어서:

  • 업무 간극을 줄이고
  • 지식 공유를 쉽게 만들고
  • “누가 머릿속으로 알고 있던 방식”을 팀이 읽을 수 있는 절차로 바꾸는

발판이 될 수 있다.

aws-deploy는 나한테 그런 첫 사례였다.

Jenkins보다 무조건 빠른 배포기를 만들었다기보다, 내가 실제로 하던 배포 과정을 내 작업 맥락 안에서 다시 프로세스화한 기록에 가깝다.
