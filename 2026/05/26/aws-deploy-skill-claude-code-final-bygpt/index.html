Jenkins 대기 시간을 약 25초 수준으로 줄이기 위해 Claude Code 스킬을 만든 기록

작성일 2026-05-26 In 인프라

대상 독자: AWS Lambda와 Step Functions를 직접 배포하는 개발자, 그리고 Claude Code를 실무에 붙여보려는 DevOps/인프라 담당자.
전제 조건: AWS CLI 설정 및 Claude Code CLI 설치 완료.

문제는 단순한 빌드 duration이 아니었다. Lambda 1개만 수정해도, 개발자가 체감하는 Jenkins 대기 시간은 생각보다 길었다.

Lambda 1개 수정 케이스에서 Jenkins는 Hook 수신부터 배포 완료까지 실측 67초였다. 평균 체감 시간으로 보면 약 2분 44초 수준이었다.

aws-deploy 스킬로 바꾼 뒤 같은 케이스에서 변경 감지 → 분석 보고 완료까지는 4.57초가 나왔다. 실제 배포를 끝내기 전, Stage 1 분석부터 Lambda 코드 zip·업로드까지 포함한 체감 총시간은 약 25초 [추정]로 보는 편이 더 보수적이다.

숫자를 바로 한 줄로 묶어 비교하면 오해가 생긴다. 4.57초는 Stage 1 분석 시간 실측값이고, 실사용 체감으로 비교하면 67초 vs 약 25초 [추정]에 더 가깝다.

이 숫자 차이가 이 글의 포인트는 아니다. 더 중요한 건 Jenkins 파이프라인에 없던 Step Functions definition 교체와 SF version·alias 핀닝이 이 스킬에는 들어 있다는 점이다. 속도를 줄인 것보다, 배포가 완결되는 기준 자체를 다시 정의했다는 쪽이 더 정확하다.

Claude Code 스킬이란

Claude Code의 Skills는 Claude Code 안에서 동작하는 마크다운 기반 프로시저다. MCP처럼 외부 서버를 띄우지 않아도 되고, .claude/commands/나 프로젝트 내부 파일로 관리할 수 있다. “배포해줘” 같은 자연어 입력이 트리거가 되고, 그 뒤에 연결된 절차를 명령과 규칙으로 실행한다. 이번 글의 aws-deploy는 CI 대체 플랫폼이라기보다, CLI에서 반복하던 배포 루틴을 재사용 가능한 프로시저로 만든 것에 가깝다.

Jenkins가 느린 두 가지 이유

Jenkins 빌드 히스토리를 보면 최소 41초, 최대 6분 18초다.

n=14 기준 평균 빌드 시간은 139.5초, 대기 포함 총 평균은 약 2분 27초다. 그런데 개발자가 체감하는 시간은 이것보다 길다.

Lambda 1개 수정 케이스 실측값이다.

구간 시각 (UTC) 소요
Hook 수신 07:03:56 —
작업 시작 (scheduled) 07:04:06 +10초
대기 (queue wait) — 7.2초
빌드 duration — 49초
Hook 수신 → 완료 67초

빌드 duration만 보면 49초지만, 개발자가 실제로 기다리는 시간은 67초다. 이 오버헤드가 평균 빌드에도 비슷하게 붙는다고 보면, n=14 평균 체감 총 소요는 약 2분 44초로 보는 편이 현실에 가깝다.

편차의 첫 번째 이유는 변경 감지 기준이다. 이 Jenkins 파이프라인도 변경된 Lambda만 추려서 배포한다. 다만 기준이 HEAD~1..HEAD 단일 커밋 diff라서 여러 커밋을 한 번에 push하면 첫 커밋 변경이 빠질 수 있고, 미커밋 변경은 아예 감지하지 못한다. 즉 차이는 “변경 Lambda 필터링 유무”가 아니라, 변경 감지 기준의 정밀도와 포함 범위에 있다.

두 번째 이유는 Hook 콜드 스타트와 파이프라인 공통 오버헤드다. git push 이후 Webhook 수신 → Jenkins 스케줄 → 큐 대기 → 실제 빌드 시작까지의 시간은 배포 대상이 1개든 10개든 앞에 붙는다.

속도만의 문제도 아니다. Lambda alias는 {ENV}-{빌드번호} 형식으로 자동 생성되고, 변경된 Lambda만 골라 배포하는 로직도 이미 있다. 하지만 Step Functions definition 교체·SF version publish·SF alias 핀닝은 파이프라인에 없었다. 즉 이 Jenkins는 변경 Lambda 선택 배포 파이프라인이긴 했지만, 서버리스 전체 배포 체인을 끝까지 묶는 자동화는 아니었다. 정확히 말하면 Lambda 코드 업로드 자동화에 더 가까운 상태였다.

전환점: “DEV에 배포해줘”가 재현한 수동 루틴

이 전환은 성능 실험에서 시작된 게 아니다. 오히려 몇 번의 우회에서 시작됐다.

AI 개발 속도가 빨라지면서 “코드 수정 → merge → Jenkins 대기 2분 44초”의 호흡이 답답해졌다. 급한 상황에서는 Jenkins를 기다리지 않고 AWS CLI로 직접 배포한 적도 몇 번 있었다. 수동이라 번거롭지만, 적어도 어떤 Lambda를 어떤 순서로 올리고 어떤 alias를 바꾸는지는 내가 즉시 통제할 수 있었다.

그러다 어느 날 Claude Code CLI에 “DEV에 배포해줘”라고 입력했더니, 내가 이전에 수동으로 밟았던 절차와 유사한 순서를 재현했다. 여기서 중요한 건 “Claude가 마법처럼 배포를 이해했다”가 아니다. 반복하던 절차가 이미 언어화 가능한 패턴이었고, 세션 문맥 안에서 그 순서를 재현할 수 있다는 게 보였다는 점이다. 그걸 보고 “이건 Skill로 굳힐 수 있겠다”는 판단이 생겼다.

그 순간 판단이 섰다.

파이프라인에서 하던 일 중 일부는 스크립트로, 나머지는 Skill로 만들 수 있겠다.

이 지점이 없으면 이 글은 빠른 배포 도구 비교로만 읽힌다. 실제로는 수동 루틴이 재사용 가능한 배포 프로시저로 응고된 과정이 핵심이다.

왜 GitHub Actions도 아니고, MCP도 아니고, Skills였나

선택지는 있었다.

  • GitHub Actions: 실행 주체가 CI 서버다. 재현성은 좋지만, 로컬 CLI 맥락과 분리된다.
  • 별도 스크립트: 동작은 만들 수 있지만, 어떤 조건에서 무엇을 판단하는지가 코드 밖으로 흩어지기 쉽다.
  • MCP 서버: 외부 도구 연동에는 좋다. 하지만 이번 문제는 외부 서버 확장보다, 로컬 작업 루틴의 코드화가 목적이었다.

이번 케이스에서 중요한 건 실행 위치였다. 배포 권한은 로컬 AWS CLI 프로파일과 작업자 맥락에 묶여 있었고, Step Functions definition 교체와 alias 정합성 확인도 로컬에서 바로 확인하는 흐름이 더 빨랐다. 즉, 필요했던 건 “또 하나의 중앙 실행 주체”가 아니라, 내가 실제로 일하는 자리에서 배포 판단과 실행을 이어붙이는 방식이었다. 그 용도에는 Skills가 가장 잘 맞았다.

스킬의 핵심: 바뀐 것만 본다

aws-deploy 스킬이 가장 먼저 하는 일은 변경 파일 목록을 만드는 것이다.

HEAD~1..HEAD 비교는 안 쓴다. 여러 커밋을 한 번에 push하면 첫 커밋 변경이 빠질 수 있기 때문이다. upstream(@{u}) → origin/{branch} → HEAD~1 순으로 fallback하고, 미커밋 변경도 합산한다.

이 목록에서 lambda-functions/{NAME}/ 패턴으로 Lambda 디렉토리를 추출한다. 이름에서 PROFILE → 환경 prefix로 치환하면 배포 대상 Lambda 이름이 나온다.

여기서 중요한 점이 하나 있다. Jenkins도 이미 비슷한 아이디어를 갖고 있다. 실제 Jenkins 파이프라인 역시 git diff --name-only HEAD~1 HEAD 기준으로 changed files를 뽑고, 그중 lambda-functions/ 경로에 해당하는 Lambda만 감지해서 배포한다. 따라서 aws-deploy의 차별점은 “Jenkins는 전체를 다 배포하고 Skill은 변경분만 배포한다”가 아니다. Jenkins는 단일 커밋 기준 변경 Lambda 필터링, aws-deploy는 upstream 기준 + 미커밋 포함 + 후속 영향 분석까지 이어지는 필터링에 가깝다.

실제 실행 결과:

lambda_function.py 파일 1개 수정 → {서비스명}-DEV-EDU-functionName 1개만 배포 대상으로 잡혔다.

4단계 배포 체인 — Lambda 코드 업로드가 끝이 아닌 이유

Lambda에 코드를 올리는 건 시작일 뿐이다. 실 트래픽이 새 코드를 타려면 publish → alias 핀닝 → Step Functions 반영이 이어져야 한다.

이 체인을 “원자적”이라고 부르면 안 된다. Stage 3 publish가 실패하면 Stage 2의 코드 업로드는 이미 반영된 상태로 남는다. 즉, 이 체인은 정합성을 맞추기 위해 순서대로 수행되는 배포 절차이지, 전체 성공/전체 롤백이 보장되는 원자 연산은 아니다.

Stage 3에서 alias 이름은 배포 시작 시 딱 1번 결정한다. 당일 날짜 기준 기존 alias SEQ 최댓값 + 1.

Stage 5가 이 체인에서 가장 중요하다. Step Functions definition 안에 Lambda ARN이 버전 없이 박혀 있거나 이전 alias를 참조하면, Lambda 코드를 올려도 Step Functions는 이전 버전을 그대로 호출한다.

같은 배포 안의 Lambda와 Step Functions가 동일한 alias 이름을 쓰게 맞추는 이유는 단순하다. Stage 5에서 definition 안의 Lambda ARN을 교체할 때, 어느 버전 세트를 묶어 배포했는지 추적 가능해야 하기 때문이다.

“배포해줘” 한 마디가 실제로 하는 일

Claude Code 터미널에서 “배포해줘”를 입력하면 스킬이 Stage 1~5를 순차 실행한다. 배포 전에 먼저 분석 결과를 보여준다.

Lambda 1개 수정했는데 SF가 2개 뜬 것은, 두 Step Functions definition 소스 파일 안에 해당 Lambda ARN이 있어서다. 스킬은 로컬 저장소 안의 Step Functions 정의 파일을 grep해서 연관 대상을 잡아낸다. 즉 “현재 AWS에 배포된 state machine 정의”를 직접 조회하는 방식이 아니라, 배포 대상이 되는 로컬 정의 파일 기준의 영향 분석이다.

이 점은 한계이기도 하다. 로컬 정의와 AWS에 이미 배포된 정의가 어긋나 있다면 영향 분석 결과도 그 차이를 그대로 안고 간다. 대신 이 글의 전제는 “정의 파일이 저장소의 기준 진실(source of truth)이다”라는 쪽에 가깝다.

이후 실제 배포가 끝나면 Stage 6 dry-run 검증까지 자동으로 이어질 수 있다. Jenkins 비교에서 이 항목이 중요한 이유는, 기존 파이프라인에는 같은 검증 단계가 별도로 없었기 때문이다.

프로젝트 확장: projects/{서비스명}.md 하나면 된다

스킬 자체는 기존 프로젝트 기준으로 만들었다. 다른 프로젝트에 붙이려면 projects/{서비스명}.md 파일 하나만 추가하면 된다.

프로젝트마다 다른 부분 — AWS profile, alias 형식, 배포 제외 Lambda 목록 — 만 여기 적고, 스킬 코어는 건드리지 않는다.

이 구조의 장점은 단순한 재사용성보다 배포 규칙의 외부화다. 원래 내 머릿속에 있던 예외와 명명 규칙이 파일로 빠져나오는 순간, 개인 루틴이 팀이 읽을 수 있는 문서로 바뀐다.

숫자는 이렇게 읽는 편이 정직하다

비교에서 가장 위험한 실수는 서로 다른 층위의 시간을 한 줄에 섞는 것이다.

이 글의 숫자는 네 종류다.

  • 67초: Jenkins의 Hook 수신 → 완료까지 최선 케이스
  • 약 2분 44초: Jenkins 평균 체감 총 소요
  • 4.57초: aws-deploy의 Stage 1 분석 완료 시간
  • 약 25초 [추정]: aws-deploy의 Stage 1 분석부터 Lambda 코드 zip·업로드까지 포함한 체감 총시간

따라서 4.57초 vs 2분 44초는 “무엇이 배포될지 파악하는 시간” 비교다. 반대로 실사용 체감으로 비교하면 67초 vs 약 25초 [추정]에 더 가깝다.

실사용 체감의 약 25초는 Lambda 1개 기준으로 Stage 1 분석부터 Lambda 코드 zip·업로드까지를 포함한 추정치다. Step Functions 후속 단계까지 실측한 숫자는 아니므로, 이 구간 역시 어디까지나 추정으로만 둔다.

Jenkins 대비 포기하는 것

이 스킬은 Jenkins를 완전히 대체하는 범용 CI가 아니다. 선택 전에 기능적 손실과 운영 리스크를 같이 봐야 한다.

기능적 손실

  • 빌드 이력 UI 없음 — Jenkins처럼 중앙 히스토리 화면이 기본 제공되지 않는다.
  • 병렬 배포 최적화 없음 — 기본 설계는 순차 실행 기준이다.
  • 알림 연동은 별도 구성 — Slack 등 배포 완료 알림은 직접 붙여야 한다.

운영 리스크

  • Claude Code 의존 — Claude Code CLI가 없는 환경에서는 실행할 수 없다.
  • 중앙 감사 추적 약화 — 누가 언제 어떤 로컬 환경에서 배포했는지를 한 화면에서 추적하기 어렵다.
  • 로컬 자격증명 의존 — AWS CLI 프로파일과 로컬 환경 상태가 배포 품질에 직접 영향을 준다.
  • 팀 표준 경로 분기 가능성 — Jenkins와 병행 운영하면 “공식 배포 경로”가 둘이 될 수 있다.
  • 거버넌스 충돌 가능성 — 승인 절차가 중요한 조직에서는 로컬 실행형 배포가 운영 통제 정책과 부딪힐 수 있다.

이 선택이 맞는 상황: 소규모 팀이 직접 배포를 관리하고, 로컬 맥락에서 빠르게 변경 감지와 배포를 이어가야 하는 경우.

Jenkins가 더 나은 상황: 여러 팀원이 독립적으로 배포하고, 중앙 UI·감사 추적·알림 체계가 필수인 경우.

결론

upstream 기준 변경 감지, Lambda alias 자동 핀닝, Step Functions definition 교체, SF version·alias 핀닝, Stage 6 dry-run 검증. aws-deploy 스킬은 Jenkins가 비워둔 일부 영역을 로컬 작업 맥락 안에서 메운다.

하지만 이 글의 결론은 “Jenkins보다 빨랐다”가 아니다.

인프라만 알던 DevOps 담당자도, MCP처럼 외부로 내보낼 필요 없이, 자신의 작업 패턴을 Skills로 코드화할 수 있다. 안정화되면 팀과 공유해서 암묵지를 명시지로 바꾸는 발판이 된다.

몇 번의 수동 AWS CLI 배포가 Claude Code 안에서 재현 가능해졌고, 그걸 Skill로 정리하는 순간 개인 루틴이 전달 가능한 프로세스로 바뀌었다. 이 글은 그 기록이다.
