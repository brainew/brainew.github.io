AI 이후, 배포는 CI 밖으로 나오기 시작했다 — Claude Code aws-deploy 스킬 사례

작성일 2026-05-26 Edited on 2026-05-27 In 인프라

기존에는 Jenkins Pipeline Job으로 Lambda를 배포했다. develop 브랜치에 PR이 머지되면 Hook으로 Pipeline이 트리거되고, 변경 감지 → 메타데이터·Layer 수집 → zip → update-function-code → version publish → alias 갱신까지 한 번에 처리한다.

이 구조 자체에는 문제가 없었다. 문제는 “구조의 위치”였다.

AI를 붙여 코딩 호흡이 빨라진 뒤로, 머지에서 배포까지의 대기 시간이 작업 흐름 밖으로 떨어져 나와 있는 게 거슬리기 시작했다. 개발은 내 손 안에서 일어나는 일이 됐는데, 배포만 여전히 “중앙 시스템이 처리하는 일”이었다.

이 글은 그 간극을 메우려고 만든 Claude Code 스킬 aws-deploy의 사례 기록이다. Jenkins 비판이 목적이 아니다. AI 시대에 배포의 행위 주체가 어디에 있어야 하는가에 대한 답을 사례 하나로 풀어보려는 글이다.

행위 주체 — Jenkins 세계관 vs Skill 세계관

기존 Pipeline은 이미 많은 일을 하고 있었다.

  1. Hook 기반 배포 브랜치 감지
  2. 작업 디렉토리 초기화
  3. 배포 브랜치 checkout·최신화
  4. merge 이전 HEAD 이후 변경사항 확인
  5. 변경된 Lambda 함수 탐지
  6. 기존 메타데이터·Layer 수집
  7. zip 압축 → 배포 → version publish → alias 갱신

이건 “zip만 올리는 스크립트”가 아니다. 변경된 Lambda만 골라내고 version·alias까지 관리하는, 충분히 잘 짜인 파이프라인이다.

문제는 자동화 품질이 아니라 행위 주체였다.

Jenkins 세계관 Skill 세계관
배포 주체 중앙 시스템 현재 작업 맥락
트리거 merge 후 hook 자연어 지시
변경 기준 Pipeline 실행 시점 upstream + 미커밋 포함 로컬
강점 다인원·감사·UI 1인 작업 호흡 친화

Jenkins는 “merge가 끝났으니 배포를 시킨다”는 모델이다. 안정적이지만, 머릿속에 “이 PR을 지금 DEV에 올려보고 싶다”는 결심이 섰을 때 그 결심과 실제 배포 사이에 한 박자 대기가 들어간다.

급할 때 Jenkins를 우회해 AWS CLI로 수동 배포를 몇 번 해봤다. 수동 배포는 위험하지만, 무엇을 왜 지금 배포하는지가 내 작업 맥락 안에 그대로 있는 감각이 있었다. 이 감각 차이가 글 전체의 출발점이다.

“현재 작업한 사항 DEV에 배포준비해줘”

수동 배포 패턴이 머릿속에 정리된 상태에서 Claude Code CLI에 이 한 줄을 입력했다.

현재 작업한 사항 DEV에 배포준비해줘

Claude Code가 내가 수동으로 밟던 순서를 그대로 밟기 시작했다. 그때 본 건 “Claude가 배포를 이해했다”가 아니라 내가 반복하던 절차가 이미 충분히 언어화 가능한 형태였다는 사실이었다.

Lambda를 찾고 → 설정과 Layer를 확인하고 → 배포 순서를 잡고 → Step Functions 영향 범위를 추적하는 흐름은 암묵지가 아니라 절차였다. 다만 그 절차를 “어떤 환경에” “지금 어느 단계까지” 적용할지 결정하는 부분만은 작업 맥락에 묶여 있었다.

여기서 LLM과 스크립트의 경계가 갈렸다.

LLM이 필요한 영역과 그렇지 않은 영역

aws-deploy의 모든 단계가 LLM 판단을 필요로 하는 건 아니다. 사실 대부분은 deterministic logic이다.

단계 담당 이유
변경 파일 감지 shell git diff 결과는 명확
Lambda 함수명 매핑 shell 디렉토리명 규칙 고정
기존 설정·Layer 조회 shell + AWS CLI API 결정적
Lambda update / publish / alias shell 명령 시퀀스 고정
SF definition 교체 / publish shell 동일
SEQ 산출 (alias 번호) shell list-aliases 결과 + 1
자연어 트리거 → 케이스 분기 Skill (LLM) “푸시했어 / 핀닝해 / DEV만 맞춰” 등 의도 해석
어느 환경에 배포할지 Skill (LLM) branch·rule·사용자 의도 해석
“준비”인지 “실행”인지 Skill (LLM) 자연어 의도 해석
SF 영향 범위 해석 Skill (LLM) 변경 Lambda ↔ 어느 SF에 박혀 있는지
프로젝트 규칙 적용 Skill (LLM) projects/{서비스}.md 읽고 alias 형식·예외 적용
변경 경로 → 케이스 자동 분류 Skill (LLM) path pattern → A/B/C/D/통합 결정

스킬을 만들면서 가장 분명해진 게 이 분리다. 변경 감지·alias 처리·SF 갱신 같은 기계적인 영역은 LLM보다 shell이 안정적이고 빠르다. LLM은 그 위에서 작업 맥락 해석과 단계 분기 판단만 한다.

자연어 트리거가 LLM 영역인 이유

스킬 메타데이터에는 한국어 구어체 트리거가 25개 넘게 등록돼 있다.

람다 배포해 / 배포 / 배포해줘 / 버전 올려 / SF 핀닝 / SF 반영 / 핀닝해 / alias 이동 / alias 갱신 / 핀닝 업데이트 / Layer 반영 / Layer 올려 / 전환경 배포 / DEV만 맞춰 / 푸시했어 / 변경사항 반영해 / 수정사항 확인해서 배포해 / 전체 배포 / 롤백 / 배포 진행해 / …

이걸 정규식이나 키워드 매칭으로 처리하면 변형마다 분기를 새로 짜야 한다. 사용자가 새로운 표현을 던지면 패턴이 깨진다. LLM은 의도 단위로 해석한다 — “푸시했어”든 “수정사항 확인해서 배포해”든 동일한 통합 배포 케이스로 매핑된다.

이 부분이 단순한 deterministic 래퍼와 LLM 기반 스킬의 본질적 차이다.

단, 이 분리가 무너지면 사고 난다. LLM이 alias 이름을 “생성”하기 시작하거나, 변경 감지를 텍스트 추론으로 처리하는 순간부터 운영 위험 영역이다. 모든 alias 번호·zip 명령·AWS CLI 호출은 shell이 결정적으로 만든다.

구현 — 변경 감지부터 SF 핀닝까지

Stage 1: 변경 감지 (shell)

aws-deploy는 upstream 기준점에 더해 push되지 않은 커밋, 워킹 트리 dirty 변경까지 모두 변경 대상으로 본다.

Jenkins는 머지 이후 중앙에서 동일 기준으로 실행되는 장점이 있다. 반면 aws-deploy는 “내가 지금 손에 들고 있는 변경”을 기준으로 본다. CLI에서 작업하는 흐름엔 이쪽이 자연스러웠다.

미커밋 변경이 있으면 분석 결과에 ⚠ 경고로 명시하고 사용자에게 진행 의사를 다시 묻는다. “그냥 zip에 포함”이 아니라 경고 후 확인이다.

lambda_function.py 1개 수정 → {서비스명}-DEV-EDU-functionName 1개만 배포 대상.

변경 파일 → 케이스 자동 분류

변경 파일 경로 패턴으로 케이스가 자동 결정된다.

경로 패턴 케이스 처리
common/lambda-functions/{프로젝트}-PROFILE-api-*/** A: Lambda만 lambda.md
common/lambda-functions/{프로젝트}-PROFILE-sf-*/** 또는 jobs/*/lambda-functions/** B: Lambda + SF 핀닝 lambda-pinning.md
layers/** C: Layer → Lambda → SF layer.md
jobs/*/stepfunctions/*.asl.json (Lambda 변경 없음) D: SF definition만 sf-only.md
2개 이상 섞임 통합 배포 full-deploy.md

API Gateway 직접 호출 Lambda(api-*)는 SF 핀닝이 필요 없고, SF 내부에서 호출되는 Lambda(sf-*, llm-*)는 핀닝까지 가야 한다. 이 분기를 사람이 매번 결정하지 않는다.

Stage 2~5: Lambda → SF 핀닝까지 한 흐름

Lambda 코드 배포 / version publish / alias 갱신은 Jenkins도 하고 있던 부분이다. 차이는 그 뒤다.

Lambda 코드를 올렸다고 Step Functions가 새 코드를 호출하지 않는다. SF definition 안에 박힌 Lambda ARN, 그 ARN의 version, state machine alias가 새 version을 가리키는지까지 같이 봐야 한다.

이 부분이 Jenkins Pipeline에는 묶여 있지 않았다. 변경 Lambda를 잘 찾는 것보다, Lambda 배포 이후 남은 서버리스 전환 작업을 한 흐름으로 묶은 것이 aws-deploy의 차이다.

alias는 같은 배포 안에서 하나로 통일된다

alias 형식은 {ENV}-{YYYYMMDD}-{SEQ} (예: DEV-20260427-1). 배포 시작 시 오늘자 alias 최댓값 + 1로 SEQ를 한 번만 결정하고, 그 배포에 포함된 모든 Lambda와 SF가 같은 SEQ를 공유한다.

실측 예: 2026-04-27 DEV 환경 13개 Lambda × 3개 SF 일괄 배포에서 모두 DEV-20260427-1 하나로 통일됐다. 사후에 “이 배포가 뭘 건드렸는지” 추적할 때 alias 하나만 보면 끝난다.

다른 프로젝트(이하 프로젝트 B)는 다르다. SF alias는 0.0.x semver만 쓴다 (백엔드가 alias 이름으로 SF를 직접 호출하기 때문). 같은 스킬 코어 위에서 이런 차이는 projects/{서비스}.md가 흡수한다.

dry-run vs write — 사전 검증으로 분리

자연어로 “배포준비” 한 줄 던졌을 때 바로 운영 리소스를 건드리면 안 된다. aws-deploy는 두 모드로 명시 분리돼 있다.

  • 배포준비 → dry-run. 변경 Lambda·영향 SF·핀닝 계획을 텍스트로만 출력. AWS write 호출 0회.
  • 배포해줘 → write. dry-run 결과를 사용자가 확인한 뒤 명시적으로 호출했을 때만 실행.

Lambda 1개 수정인데 SF가 2개 잡힌 건 두 SF의 definition 안에 해당 Lambda ARN이 박혀 있어서다. 영향 범위를 사람이 추적할 필요가 없다.

이 모드 분리가 없으면 Skill을 운영 도구로 쓸 수 없다. 자연어 → 즉시 write 구조는 한 번이라도 사고나면 다시 못 쓴다.

프로젝트 규칙 — projects/{서비스}.md

다른 프로젝트에 붙일 때는 스킬 코어를 안 건드리고 파일 하나만 추가한다. 현재 두 개 프로젝트(A·B)가 같은 스킬 코어를 공유하고, 차이만 각자의 파일에 들어간다.

가치는 재사용성보다 머릿속 예외와 명명 규칙이 파일로 빠져나오는 순간 개인 루틴이 팀이 읽을 수 있는 절차가 된다는 점이다.

운영 안전 가드레일 — 6개 절대 원칙

스킬을 운영에서 쓰려면 LLM 판단이 들어가는 자리에 가드레일이 명시적으로 박혀 있어야 한다. aws-deploy의 6개 원칙은 실측 사고 후에 한 줄씩 추가된 것들이다.

  1. “배포 완료” 단어 사용 조건 — Lambda version publish + alias 생성 + SF update + publish + alias 교체 + describe 재검증이 전부 성공한 후에만. 다단계 검증 누락 → “배포 완료” 단어 금지.
  2. PROD alias 보호 — 현재 활성 alias는 명시적 사용자 확인 없이 수정 금지. PROD 신규 alias 생성도 동일.
  3. 환경 추측 금지 — “배포해”만 들리면 “DEV만? PROD도?” 자동으로 되묻는다. 추론으로 환경 결정 금지.
  4. 항상 배포 제외 목록 — triggerHandler 등 정책상 제외 Lambda는 변경 감지 단계에서 자동으로 떨궈진다. LLM이 “이것도 같이 배포할까요?” 묻지 않는다.
  5. 확인 응답 프로토콜 — “완료/맞다” 단독 답변 금지. 반드시 version 번호 + alias 이름 + ARN 같은 근거 + 미확인 범위 명시.
  6. git 쓰기 작업 read-only — git diff, git show, git branch --show-current만 사용. commit·push·tag는 사용자가 직접. 유일한 예외는 Layer 배포 후 자동 갱신되는 LAMBDA-{ENV}-LAYERS.yml 한 파일을 Stage 6에서 자동 commit/push하는 부분. 이마저 push 실패 시 자동 pull/rebase 금지 — 실패만 보고하고 사용자 수동 처리.

이 6개는 LLM이 알아서 잘하기를 기대하지 않는다는 원칙으로 만들어졌다. 자연어 의도 해석은 LLM에 맡기되, 운영 리소스에 닿는 모든 결정은 명시적 확인을 거친다.

한 단계 더 — “어느 SF에 영향이 가는지” 같은 판단도 LLM의 추론이 아니라 grep -l 'PROFILE-{name}' jobs/*/stepfunctions/*.asl.json 같은 결정적 명령의 결과를 LLM이 사용자에게 옮기는 구조다.

숫자 — 보수적으로

속도가 본질은 아니지만 측정은 한다.

항목 Jenkins aws-deploy
Lambda 1개 수정 E2E 67초 실측 Stage 1 4.57초 실측
전체 평균 (n=14, 대기 포함) 약 2분 27초 별도 E2E 실측 필요
변경 감지 기준 Pipeline 실행 시점 upstream + 미커밋
Lambda version·alias 있음 있음
SF definition·version·alias 없음 (수동) 자동
dry-run 없음 사전 영향 분석
프로젝트 추가 Jenkinsfile 복사·수정 projects/{name}.md

4.57초는 분석 시간이지 E2E가 아니다. 실제 write까지 포함한 전체 시간은 LLM 응답 상황에 따라 Jenkins보다 더 오래 걸리는 경우도 있다. 1건만 배포하는 케이스라면 더 그렇다.

숫자는 계기였지 결론이 아니다. 진짜 변화는 배포가 작업 호흡 안으로 들어왔다는 쪽이다.

한계 — 이 방식이 안 맞는 상황

이 스킬은 범용 CI가 아니다.

  • 로컬 AWS 자격증명 의존 — rotate·관리 책임이 개인에게 옴
  • 로컬 dirty tree까지 배포 대상 — 편하지만 미커밋 변경이 운영에 올라갈 수 있음
  • 중앙 감사 추적 약함 — “누가 언제 무엇을 배포했는지” 한 군데서 보기 어려움
  • 공식 배포 경로 이원화 위험 — Jenkins와 병행 운영 시 누구는 hook, 누구는 Skill로 갈라짐

aws-deploy는 소수 인원이 직접 배포를 관리하고 로컬 작업 맥락에서 변경 분석과 배포 준비를 빠르게 이어가야 하는 경우에 맞는다. 다수 팀원이 독립적으로 배포하고 중앙 UI·감사·알림 체계가 중요하다면 Jenkins가 더 맞다.

자주 받는 질문에 대한 현재 상태

  • rollback: 공식 자동 서브플로우는 없다. 현재 구조에서 rollback은 alias routing을 이전 version ARN으로 되돌리는 ad-hoc 절차다. _sf-5-step-chain.md와 _lambda-publish-alias-pc.md에 명령 패턴은 있지만, “rollback해줘” 한 줄로 자동 복원되는 흐름은 아직 없다. 트리거 단어(“롤백”)는 등록돼 있어 LLM이 이전 alias 매핑을 보여주고 사용자가 명시적으로 명령을 확정한다.
  • 여러 사람이 동시 배포: 현재 alias 충돌 보호 없음. 1인 사용 전제. (SEQ는 같은 날 같은 환경의 alias 최댓값 + 1로 결정되지만, 동시 실행 시 race condition까지는 막지 않는다.)
  • secrets: Skill prompt에 자격증명 직접 박지 않음. 로컬 ~/.aws/credentials만 참조.
  • shell 권한 범위: Claude Code Bash tool 권한 그대로. dry-run은 read-only AWS API만, write 단계 진입 시 절대 원칙 3·5에 따른 사용자 확인 필요.
  • 무한 루프 방지: Layer 배포 후 자동 commit되는 LAMBDA-{ENV}-LAYERS.yml이 다음 배포에서 또 변경으로 잡히지 않도록, 변경 감지 단계에서 이 파일은 항상 필터링된다.
  • 5개 SF 동시 describe 사고: 과거에 5개 SF를 동시에 describe-state-machine 호출했을 때 1개 SF가 StateMachineDoesNotExist로 실패하자 같은 메시지 블록 내 후속 호출이 cancel된 적이 있다. 이후 단계 0에서 미존재 SF를 사전 필터링하는 절차가 들어갔다.

마무리

이 글의 핵심은 “Jenkins보다 빠른 배포 도구를 만들었다”가 아니다.

AI 이후, 배포의 행위 주체가 중앙 시스템에서 작업 맥락 쪽으로 옮겨간다.

LLM이 모든 단계를 판단할 필요는 없다. 변경 감지·alias 처리 같은 결정적 영역은 shell이 더 안정적이다. LLM이 들어가야 할 자리는 어디로 / 얼마나 / 언제까지 같은 작업 맥락 해석이다. 그 자리에 들어가는 순간 “merge 후 배포”가 “작업 흐름 내부 배포”로 모양을 바꾼다.

이건 단순히 한 도구를 다른 도구로 교체한 이야기가 아니다. CI는 중앙 시스템에서만 돌아간다는 전제 자체가 흔들리기 시작했다는 신호에 가깝다. 배포가 merge 이후 별도 stage가 아니라 작업 흐름의 일부가 될 때, 인간이 직접 orchestration하는 영역은 줄어들고 intent를 전달하는 영역이 늘어난다. CI/CD라는 개념의 경계 자체가 재편되는 중이다.

aws-deploy는 그 재편의 한 단면을 1인 워크플로우에서 본 기록이다. 다른 환경에서는 다른 모양일 거고, 더 좋은 답이 곧 나올 거다. 다만 지금 시점에서 한 가지는 분명하다 — 배포는 더 이상 중앙 시스템만의 일이 아니다.
