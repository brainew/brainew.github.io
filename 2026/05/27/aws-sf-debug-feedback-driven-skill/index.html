LLM이 '이렇게 수정하실래요?'라고 묻기 시작한 순간 — 사용자 피드백으로 진화한 SF 디버그·배포 자매 스킬

작성일 2026-05-27 In 인프라

이전 글에서 aws-deploy 스킬 사례를 풀었다. 그 글의 핵심은 배포 workflow의 행위 주체 이동이었다. 이번 글은 그 workflow 안에 운영 패턴이 어떻게 누적되는지에 대한 기록이다.

{PROJECT}-ERROR-E005-{ID}-{TIMESTAMP} 같은 형태의 searchKey 패턴이 있다. 내가 만든 인프라다. LLM이 발명한 게 아니라, SF의 Catch가 잘못 잡혀 에러가 silent로 증발하는 사고를 막으려고 모든 실패 경로에 박아둔 deterministic key다.

그 위에서 “이 searchKey로 에러 찾아줘”를 반복 던지다 보니, 어느 순간 응답 구조가 달라지기 시작했다.

“에러 찾았고, 이건 이렇게 수정하면 될 것 같은데 진행할까요?”

찾기만 하던 흐름이 수정 제안까지 포함하는 흐름으로 확장된 순간이다. 그 확장 + 거기서 누적된 디버그 → hotfix → 배포 자율 사이클이 본 글의 주제다.

스킬 문서에는 처음부터 이렇게 박혀 있었다.

“이 스킬은 완성형이 아니다 — 사용자 피드백으로 계속 성장한다.”

그 글귀가 어떻게 사실이 됐는지의 기록. *LLM의 진화가 아니라 feedback이 skill 문서와 workflow에 누적된 결과를 다룬다.*

시작점 — searchKey는 LLM이 아닌 내가 만든 deterministic 인프라

서버리스 환경에서 SF + Lambda로 서비스 로직을 짜다 보면 한 번쯤 부딪히는 문제가 있다.

  • 같은 Lambda(재사용 가능)도 어떤 SF에서 호출됐냐에 따라 봐야 하는 부분이 달라진다
  • SF의 각 Task Catch가 잘못 잡혀 있으면 실패가 성공처럼 표현되고 증발한다

이 두 패턴이 누적되면 에러가 일어났는지조차 모르는 silent failure가 쌓인다. 그래서 모든 Lambda 실패 경로에 들어가는 고유 key를 만들었다.

  • {PROJECT}: 어느 프로젝트의 에러인지 (멀티 프로젝트 운영)
  • E{CODE}: 에러 코드 (E005, E014 등 SF 단계별 책임 코드)
  • {ID}: 에러 발생 대상 식별자 (job id 또는 input의 핵심 식별자)
  • {TIMESTAMP}: 발생 시각 (밀리초)
  • {SUFFIX}: 중복 회피용

SF Catch 블록 안에서 JSONata로 즉시 발급된다. 한 줄짜리 표현 두 종.

이 searchKey가 SNS로 publish되고, 그 메시지가 EventBridge를 거쳐 MongoDB error_logs 컬렉션에 적재된다. CloudWatch Logs에도 같은 키가 박힌다 — Lambda Layer로 공통 logger를 만들어 모든 Lambda가 같은 형태로 찍는다.

표준 Catch 블록은 이렇게 생겼다 (이름 placeholder 적용).

📋 Catch + SNS Publish ASL 전체 (JSON, 22줄) — 펼치기

핵심은 두 가지.

  1. ErrorEquals: ["States.ALL"] — 어떤 실패든 떨어뜨리지 않는다. silent failure 차단.
  2. searchKey가 메시지 본문에 박힌다 — SNS → EventBridge → DB로 흘러가는 동안 같은 키로 join 가능.

이게 글 전체의 토대다. LLM이 등장하기 전부터 있었고, LLM이 만든 게 아니다.

반복 — “에러 찾아줘”를 던질수록 LLM이 분석 깊이·수정 기준까지 학습

처음엔 단순했다. 에러가 SF console에 뜨면 searchKey를 복사해서 LLM에게 던졌다.

{PROJECT_A}-ERROR-E005-12345-20260514072830_a1b2c3d4 이거 왜 실패?

LLM이 가는 경로는 매번 비슷했다.

레이어 무엇을 봤는지
L1 describe-execution — status, error, cause
L2 get-execution-history — 전체 event stream
L3 Map state iteration 단위 (Inline)
L4 Distributed Map child execution 재귀
L5 TaskScheduled event의 requestId로 CloudWatch Logs 매칭
L6 외부 SaaS 응답 / DB / SNS / S3 실패 분류
L7 재처리 (redrive / 수동 invoke / 캐시 무효화)

처음엔 내가 “L1만 보지 말고 L5까지 가서 Lambda 로그도 봐줘”라고 매번 지시했다. 두세 번 반복하니 LLM이 알아서 L7까지 들어가기 시작했다. 그 다음 세션부터는 “에러 찾아줘”만 던져도 같은 깊이로 갔다.

CloudWatch에는 공통 Layer의 logger가 구조화된 JSON으로 찍는다. 이하 코드는 searchKey 하나가 SF console·CloudWatch Logs·MongoDB·대시보드 4-system을 어떻게 연결하는지의 단면이다.

CloudWatch에 떨어지는 raw 로그 한 줄.

이게 모니터링 대시보드 페이지의 ErrorSearch로 들어온다. 페이지 type 정의 일부.

📋 ErrorLogItem TypeScript 인터페이스 (15줄) — 펼치기

searchKey 하나로 SF console / CloudWatch Logs / MongoDB / 대시보드 네 시스템을 join 한다. LLM이 분석할 때 이 key 하나로 4-system 추적이 가능하다 — 가능성을 내가 만들어 둔 거고, LLM은 그걸 사용할 뿐.

다만 사용하는 깊이를 반복하면서 내 분석 패턴이 LLM 응답에 새겨졌다.

전환점 — 분석에서 수정 제안까지 흐름 확장

어느 시점부터 응답이 길어졌다.

L1~L7 분석 후 “근본 원인: Lambda {FUNC_NAME} 내부의 index.mjs:26에서 강제 throw + 상위 SF의 Catch가 [States.ALL → Success]로 잡혀 있어 silent failure 발생”까지 가는 건 같았다. 거기서 끝났던 게, 어느 순간 한 단락이 더 붙기 시작했다.

“수정 방향: Lambda의 강제 throw 제거 + SF Catch를 SNS Publish (Fail) 경로로 변경 + failedLambda 필드 PROFILE → DEV 정정. hotfix 브랜치 hotfix/E005-{FUNC_NAME}-throw-restore 만들어서 진행할까요?”

내가 명시적으로 가르친 적이 없는 흐름이다. 내가 직접 hotfix를 짜왔던 과거 세션들의 패턴이 skill 문서와 응답 컨텍스트에 누적된 결과에 더 가깝다 [추정]. 정확한 경로는 확인 어렵지만, 결과는 명확하다.

/Users/brainew/Documents/dev/ai/agent_team/aws-sf-debug/integration.md에는 그 흐름이 표준화되어 박혔다 — E1~E9라는 사이클로.

자율 진행은 E6까지. E7에서 STOP. PR 머지는 내가 명시 트리거(머지했어)를 던지기 전까지 다음 단계로 안 간다.

이 가드레일은 처음부터 있었던 게 아니다. 과거에 “계속 진행해” 같은 막연한 명령에서 LLM이 PR을 자동 머지해 사고가 났던 기록이 메모리에 남아 있고, 그 사고 후에 feedback_pr-merge-user-only라는 규칙이 박혔다. 그 규칙이 다시 본 스킬의 integration.md에 흡수됐다.

즉, 내가 한 번 실패한 패턴이 스킬에 가드레일로 들어왔다. 이 자체가 “사용자 피드백으로 진화한다”의 한 사례다.

귀결 — skill 자체에 사용자 운영 패턴이 새겨진다

스킬 문서 (SKILL.md)에는 별도 섹션이 박혀 있다.

추상적 글귀가 아니라 실제로 그렇게 돌아간다. 사례 하나.

2026-05-14 검증 세션에서 한 SF가 silent failure 패턴을 보였다 — 한 Task의 Catch가 [States.ALL → Success]로 잡혀 있어 실패가 통과로 표시됐다. hotfix로 그 1개를 정정하고 끝낼 수도 있었는데, 내가 한 줄 던졌다.

“{PROJECT_B}도 모든 task의 에러에서 Catch로 빠지고 fail SNS 발행되게 되어있는지 체크해와”

LLM이 ASL 9개 State를 전수 점검하고, 누락된 9개 State에 동일 패턴 Catch를 일괄 보강한 PR을 만들었다. 단순 1건 hotfix가 운영 안전 정비로 확장됐다.

이때 만든 9개 State 매핑.

이 사례가 끝나고, 비슷한 *”silent Catch가 다른 SF에도 박혀 있을 수 있다”*는 학습이 heuristics.md에 추가됐다. 다음 세션의 첫 SF describe에서 LLM이 알아서 Catch 패턴을 체크하기 시작했다.

이게 글이 말하려는 핵심이다. LLM이 새 능력을 갖춘 게 아니라, 내 운영 결정 기준이 스킬 문서에 누적되어 다음 세션에도 그 흐름이 그대로 적용된다.

연계 — 사람 머지를 가드레일로 두고 자매 스킬로 인계

E1~E9 흐름의 시각화.

여기서 행위 주체는 두 번 바뀐다.

  • E1~E6: LLM (분석 + hotfix 작성)
  • E7: 사람 (PR 리뷰 + 머지)
  • E8: LLM (배포 자동화)

사람이 끼는 자리는 운영 변경이 시작되는 정확한 순간이다. 그 자리에 가드레일이 있는 한, 자율 사이클은 운영 위험과 분리된다.

자매 스킬로 넘어가는 트리거도 자연어 한 줄이다.

이전 글에서 다룬 aws-deploy의 Stage 1 변경 감지가 이 시점에서 발동된다. git diff 결과 + 케이스 자동 분류 → 5단계 체인.

검증 — 재검증으로 사이클 닫음

분석·hotfix·배포가 끝나면 실제로 동작이 정정됐는지 확인하는 단계가 남는다. aws-sf-debug 스킬로 다시 진입해서 manual replay로 새 트리거 1건을 실 운영 활성 alias에 흘려본다.

2026-05-14 양 프로젝트 검증 결과 (사내 검증 기록 인용).

프로젝트 execution 소요 결과
{PROJECT_A} (활성 alias → 새 SF version) {EXEC_NAME_1} 8분 28초 SUCCEEDED
{PROJECT_B} (활성 alias → 새 SF version) {EXEC_NAME_2} 6분 35초 SUCCEEDED

측정 방법: SF console의 execution duration 직접 인용. manual replay는 start-execution API 직접 호출 + input은 운영 실 트래픽 인용. 표본은 양 프로젝트 각 1건 — 통계적 검증이 아니라 사이클 동작 확인이다.

검증 자체는 ErrorSearch 대시보드에서 searchKey deep link로 재진입 가능하다.

같은 키로 SF execution + Lambda Logs + DB + 대시보드 4-system이 다시 join된다. 사이클 끝.

같은 검증 세션에서 만들어진 누적 PR 7개의 상태.

PR 종류 머지 목적
강제 후퇴 setup (양 프로젝트 2개) MERGED 검증용 silent failure 유도
임의 복원 PR 1개 DECLINED 사용자 명시 동의 없이 작성 — 거부됨
자동 hotfix PR (LLM 작성, 양 프로젝트 2개) MERGED E5에서 자동 생성, E7에서 사람 머지
운영 안전 보강 PR 1개 MERGED 9개 State 정공 Catch 일괄

DECLINED PR이 1개 있다. LLM이 사용자 명시 동의 없이 임의 복원 PR을 만들었고, 그게 거부됐다. 그 사건 이후 feedback_pr-merge-user-only가 integration.md에 더 강하게 박혔다. 가드레일 자체도 사용자 피드백으로 진화한다.

마무리

이전 글이 행위 주체가 중앙 시스템에서 작업 맥락으로 옮겨간다였다면, 이번 글은 한 단계 더 들어간 이야기다.

LLM이 새 능력을 갖춘 게 아니다. 내가 반복한 분석 깊이와 수정 결정 기준이 스킬 문서에 누적됐고, 다음 세션에도 그 흐름이 그대로 적용될 뿐이다.

스킬은 도구가 아니라 내 운영 패턴이 누적되는 자리다. searchKey 같은 deterministic 인프라가 아래에 깔려 있고, 그 위에서 자연어 트리거 한 줄로 분석·hotfix·배포가 자율 사이클이 된다. 사람이 끼는 자리는 운영 변경이 시작되는 정확한 순간 — PR 머지. 그 가드레일 한 점이 있는 한, 자율 사이클은 운영 위험과 분리된다.

내가 한 번 실패하거나 사용자가 한 번 지적한 패턴이 스킬 문서에 박혀 다음 세션 첫 줄부터 적용된다. 이게 “사용자 피드백으로 진화한다”는 글귀의 진짜 의미였다.

이건 아직 개인 운영 workflow 수준의 사례다. 다만 그 자리에서 feedback이 인프라가 되는 한 단면은 분명히 보인다. aws-sf-debug와 aws-deploy는 나한테 그 첫 사례였다.
