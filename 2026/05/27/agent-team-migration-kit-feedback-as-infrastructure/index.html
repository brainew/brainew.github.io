feedback이 인프라가 되고, 인프라는 마이그레이션 단위가 된다 — agent team 키트 v2.2 사례

작성일 2026-05-27 In 인프라

1편은 workflow 행위 주체 이동, 2편은 skill에 운영 패턴이 누적되는 과정이었다. 이번 글은 한 단계 더 나아간다 — 누적된 패턴이 마이그레이션 가능한 단위가 되는 사례.

키트 한 묶음(agent-team-migration-kit v2.2, 41 파일, 364KB)을 다른 머신으로 옮기고 install 스크립트 두세 줄을 돌리면 동일한 작업 환경이 재현된다. 튜토리얼이 아니라 install 스크립트가 인계 매체다.

이 글은 그 키트가 어떻게 v1 → v2.2로 자라났는지, 어느 사용자 피드백이 키트 어디에 박혔는지의 기록.

시작점 — sub-agent가 사용자 룰을 못 본다

Claude Code v2.1.32+의 Agent Teams 실험 기능을 켜면, main 세션이 leader가 되어 1~4명의 sub-agent를 별도 tmux pane에 spawn한다. Phase × Sub-stage 단위로 작업을 나눠 자동 연쇄 진행. 1편의 aws-deploy / 2편의 aws-sf-debug 모두 main 세션 1개의 흐름이었는데, 이제 작업 단위가 팀으로 늘어난 셈.

여기서 첫 문제가 드러난다.

main session은 CLAUDE.md / 룰 / 메모리를 자동 로드하지만 spawn된 sub-agent는 별개 컨텍스트라 사용자 룰 / 도메인 피드백이 자동 전달되지 않는다. 매 spawn마다 prompt에 수동 inject하면 누락이 잦다.

1편·2편에서 누적한 사용자 결정 기준(예: feedback_pr-merge-user-only, feedback_alias-preserve)이 sub-agent에선 처음 일하는 새 사람에게 다시 가르치는 꼴이 된다. 매번 prompt에 박아넣으면 누락이 자주 나고, 결국 sub-agent가 main이 이미 학습한 함정을 다시 밟는다.

첫 해결책 — Skill 패턴 미러로 Agent Rules Overlay 도입 (v2.1)

해결책은 단순했다. **2편에서 다룬 skill에 패턴이 누적되는 메커니즘을 sub-agent에도 그대로 미러링**한다. 모든 sub-agent가 spawn 직후 글로벌 단일 진실을 Read하게 만들어, 사용자 룰·feedback을 자동 흡수.

v2.1에서 도입된 흐름 4단계.

  1. install-overlay.sh가 ~/.claude/agent-rules-overlay.md를 글로벌 단일 진실로 적재
  2. normalize-agent-tools.py가 모든 sub-agent .md 본문 첫 줄에 marker로 overlay Read hook을 멱등 inject
  3. sub-agent는 spawn 직후 본 overlay를 Read → 사용자 룰 + §3 도메인 매핑된 feedback_*.md 적재
  4. 새 사고/피드백이 발견되면 feedback_<slug>.md 한 파일 + overlay §3 매핑 1행 추가만 하면 다음 spawn부터 자동 적용. agent .md 본문은 손대지 않음.

overlay 자체 구조는 이렇게 생겼다.

📋 agent-rules-overlay.md.tmpl 구조 — 펼치기

핵심은 멱등 inject. install-overlay.sh를 몇 번을 다시 돌려도 sub-agent .md에 중복 hook 안 박힌다. v2.1 시점에 이 메커니즘 자체가 키트의 주력 자산이 됐다.

v2.1 → v2.2 — feedback이 키트에 직접 새겨지다

v2.1로 한동안 운영하다 보니 키트 자체에 박혀야 할 새 피드백이 5건 누적됐다. 그게 v2.2 (2026-05-15)로 묶였다.

# 사용자 피드백 트리거 v2.2 반영
1 “세션당 cache read 252k 누적 — 토큰 비용 너무 큼” OPTIMIZATION.md (8KB) + optimize-agent-descriptions.py + audit-skills.sh 신규
2 “agents description이 spawn 결정 부하의 큰 부분” 16개 agent description 압축 매핑 JSON — 41,450 bytes → 7,582 bytes (-82%) 실측
3 “재실행 안전성 미보장 — 한 번 더 돌리면 망가질 듯” 멱등성 marker <!-- DESCRIPTION_COMPRESSED_v1 --> + .archive-pre-compress/ 자동 백업 + restore-agent-descriptions.sh
4 “skills 자동 로드도 토큰 무거움” audit-skills.sh — 사용 패턴 분석 후 archive 후보 추천만 출력, mv는 사용자가 직접
5 “v1 → v2 이관 시 agent 36 → 26 정리 흔적이 안 남음” CHANGES.md 신규 + v2/v2.1/v2.2 entry append 패턴 정립

5건 모두 튜토리얼에 한 줄 추가가 아니라 스크립트·템플릿·changelog 패턴 자체로 박혔다. 다음 사용자가 키트를 받아도 CHANGES.md만 읽으면 왜 그 스크립트가 그 자리에 있는지가 그대로 따라온다.

특히 #2의 토큰 압축 수치는 그대로 노출.

📋 optimize-agent-descriptions.py — frontmatter 압축 핵심 (Python, 14줄) — 펼치기

description만 교체. 본문(system prompt body)은 손대지 않는다 — sub-agent 실제 동작에 영향 0 + 토큰만 절감.

환경 복제 — install 두세 줄로 끝난다

키트가 한 묶음으로 완결됐다는 건 install 흐름 자체가 사용자 인계 매체가 됐다는 뜻. 다른 머신·다른 사람이 README 따라하는 게 아니라 셸 스크립트를 돌린다.

세 단계.

단계 스크립트 무엇이 일어나는지 검증
1 install-overlay.sh ~/.claude/agent-rules-overlay.md 적재 + §3 매핑 가이드 grep AGENT_RULES_OVERLAY_v1 count
2 install-agents.sh 프로젝트 20 agent 설치 (npx claude-code-templates) + tools 표준화 + overlay hook 멱등 inject ls ./.claude/agents/*.md | wc -l = 20
3 install-globals.sh (옵션) 글로벌 6 보조 agent 설치 (planner / tdd-guide / e2e-runner 등) ls ~/.claude/agents/*.md | wc -l ≥ 6

각 스크립트 본체는 단순한 셸 흐름이다.

📋 install-agents.sh 핵심 — agents 설치 + tools 표준화 (Bash, 21줄) — 펼치기

설치 후 verify-setup.sh로 A~G 단계 자동 점검. 단 하나라도 FAIL이면 자동 연쇄 진입 차단.

📋 verify-setup.sh — Agent Teams 환경 점검 (Bash, 17줄) — 펼치기

여기서 deny 패턴 강제가 핵심이다. 글로벌 settings.json에 Bash(rm -rf *) / Bash(sudo *) / Bash(aws * delete-* *) 같은 deny가 박혀 있어야 bypassPermissions 모드에서도 위험 도구가 차단된다.

📋 settings.global.json + settings.local.json 스키마 — 펼치기

글로벌 = 위험 차단의 단일 진실, 프로젝트 = 작업 편의를 위한 광범위 allow. 이 분리 자체가 키트 안에서 1인 작업 환경과 운영 안전 사이 균형점이다.

설치 총 30분(빠른 시작 기준), CHECKLIST A~K 풀 진행 시 약 50분.

검증 — 자동 연쇄가 다른 머신에서도 작동했나

키트가 복제 가능한 단위라는 주장은 실 검증이 필요하다. v2 sprint에서 그 검증이 이뤄졌다.

토큰 최적화 검증 (2026-05-14) description 41,450 → 7,582 bytes (-82%), skills 24KB → 4.5KB (-81%) v2.2 직전 측정

특히 v2 sprint ALL PASS 9/9는 다른 의미가 있다. 키트 시점에 박혀 있던 모든 가드레일(feedback_pr-merge-user-only, verification-loop, tdd-workflow, systematic-debugging)이 sub-agent별개 컨텍스트에서도 그대로 작동했다는 뜻. 즉 1편·2편 자산이 키트 안에서도 살아 있다.

시리즈 자산 키트 안 위치 동작 방식
aws-deploy / aws-sf-debug 스킬 키트가 가정하는 권장 활성 17 skill 중 일부 (CHANGES.md / OPTIMIZATION.md 인용) 1·2편의 배포·디버그 사이클이 키트 환경에서도 같은 트리거로 작동
feedback_pr-merge-user-only 규칙 overlay 템플릿 §3 도메인×피드백 매핑 sub-agent가 PR 머지 권한을 임의 행사 못하게 spawn 직후 자동 흡수
verification-loop / verification-before-completion CHECKLIST.md E·H 단계 + OPTIMIZATION.md §3.2 토큰 최적화 후 기능 회귀 검증 강제 — 새 사용자도 같은 게이트 통과
tdd-workflow / systematic-debugging README.md 검증 사례 + PATTERNS.md v2 sprint P0 closing 패턴이 키트 안 가이드 문서로 박힘

즉, 키트는 agent 정의 + settings + overlay만 옮기는 게 아니라 1·2편에서 누적한 운영 결정 기준 전체를 옮긴다.

마무리

1편이 workflow 행위 주체 이동, 2편이 feedback이 skill에 누적이었다. 3편의 한 줄은:

feedback이 충분히 누적되면 그 인프라 전체가 마이그레이션 단위가 된다.

키트는 단순한 dotfiles가 아니다. 1편의 deterministic 배포 흐름, 2편의 디버그·hotfix 사이클, 그 위 누적된 모든 사용자 결정 기준이 install 스크립트 두세 줄로 다른 머신에 옮겨간다. README가 인계 매체였던 시대에서, .sh가 인계 매체가 되는 시대로 한 발 더 옮겨간 셈.

이건 아직 1인 운영 환경 한 묶음의 사례다. 다만 그 자리에서 운영 환경이 install 스크립트로 인계되는 한 단면은 분명히 보인다. 다른 사람이 README 읽고 따라하는 게 아니라 셸 한 줄로 환경을 복제하는 흐름은, 시리즈 1·2편 결말이 자연스럽게 도달한 다음 단계다.

agent-team-migration-kit은 그 다음 단계의 한 단면이다.
